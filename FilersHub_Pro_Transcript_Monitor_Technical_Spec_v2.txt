1. Executive Summary
FilersHub Pro Transcript Monitor is a premium feature that enables tax professionals to automatically monitor their clients’ IRS account transcripts and receive real-time alerts when specific transaction codes appear. This eliminates the need to manually pull and review transcripts, saving hours of staff time and ensuring nothing falls through the cracks.
The system integrates with the IRS e-Services Transcript Delivery System (TDS) API using the ISP (Intermediate Service Provider) authorization flow, polls transcripts multiple times daily, and delivers customizable alerts through GoHighLevel workflows.
Target users: Tax professionals (EAs, CPAs, tax attorneys) who are FilersHub Pro subscribers and have active IRS e-Services accounts.
Delivery model: FilersHub Pro feature, initially deployed as a private GHL integration for resale, with future migration to standalone FilersHub platform.

2. IRS e-Services API Authorization
Because FilersHub is a third-party application selling access to other tax professionals, we must use the ISP (Intermediate Service Provider) authorization flow. This is required by IRS policy — the A2A flow is only for organizations not reselling their product.
2.1 ISP Flow Overview
The ISP flow is an OAuth 2.0 authorization code grant. The tax professional logs into IRS, grants consent to FilersHub’s Client ID, and the IRS returns an authorization code that gets exchanged for access tokens.
2.2 Registration Requirements
	•	Complete Secure Access registration for e-Services (FilersHub principal)
	•	Submit API Client ID Application through e-Services portal
	•	Provide JWKs file with valid X.509 digital security certificate
	•	Provide redirect URI (FilersHub callback endpoint)
	•	Receive Client ID upon approval
For questions about the Client ID application, contact IRS e-Help Desk: 1-866-255-0654.
2.3 Certificate Requirements (JWK)
The JWK must contain an RSA public key with the following required attributes: kty (Key Type), kid (Key ID), use set to “sig”, n (modulus), e (public exponent set to “AQAB”), x5c (X.509 Certificate Chain), and x5t (X.509 Certificate SHA-1 Thumbprint). If any attribute is missing, the JWK is invalid. FilersHub is responsible for tracking expiration and providing a replacement before expiry.

2.6 Rate Limiting
The IRS imposes a consumption limit on API calls. Exceeding the limit triggers a 10-minute blackout period with HTTP 429 status code. Our polling scheduler must account for this across all monitored users to avoid hitting limits.
2.7 ISP Authorization Flow Steps (for each user)
	•	User clicks “Connect to IRS” in FilersHub Pro settings
	•	FilersHub redirects user to IRS authorization endpoint with Client ID and response_type=code
	•	User logs into IRS and grants consent to FilersHub’s Client ID
	•	IRS redirects back to FilersHub callback URI with authorization code
	•	FilersHub backend exchanges auth code + Client JWT for access token and refresh token
	•	Tokens are encrypted and stored in Supabase for scheduled polling

3.2 High-Level Data Flow
	•	VPS cron job fires 3–4 times daily
	•	Polling service queries active monitored clients from Supabase
	•	For each client, retrieves stored IRS tokens (decrypted from Vault)
	•	Refreshes access token if expired (using stored refresh token)
	•	Calls TDS API to pull account transcript for each monitored TIN
	•	Parses transcript response and extracts transaction codes
	•	Compares codes against last known snapshot stored in database
	•	For any new codes: checks user’s alert preferences
	•	If code matches an enabled alert, fires notification via GHL API
	•	Updates stored transcript snapshot with latest data

5. Feature Specifications

A guided setup flow in FilersHub Pro settings that walks the user through connecting their IRS e-Services account.

6. Polling Engine Design
6.1 Scheduling
A dedicated VPS runs the polling service as a scheduled cron process. This avoids Edge Function cold start issues and supports polling hundreds of clients reliably. Recommended polling frequency: every 6 hours (4 times daily) to stay well within IRS rate limits.
6.2 Batch Processing
The polling engine must process users in batches to avoid overwhelming the IRS API and hitting rate limits. Recommended approach:
	•	Process users sequentially, not in parallel
	•	Add a delay between API calls (e.g. 2–3 seconds)
	•	Track the IRS rate limit and back off if HTTP 429 is received (10-minute blackout)
	•	Log all API calls and responses for debugging

6.3 Token Refresh Logic
Before each API call, the engine checks if the stored access token is still valid. If expired, it attempts a refresh using the stored refresh token. If the refresh token is also expired (after 1 hour), the system marks the user’s connection as “expired” and sends them a notification to re-authenticate.
6.4 Change Detection Algorithm
	•	Pull current transcript from TDS API
	•	Parse transaction codes from response
	•	Load previous snapshot from transcript_snapshots table
	•	Compare: identify codes present in new response but absent from previous snapshot
	•	For each new code, check if user has that code’s alert enabled in alert_preferences
	•	If enabled, create alert_log entry and fire GHL notification
	•	Save new snapshot to transcript_snapshots (overwrite previous)

7. Security Requirements
This system handles taxpayer PII (TINs) and IRS authentication credentials. Security is non-negotiable.
7.1 Data Encryption
	•	IRS access tokens and refresh tokens: stored in Supabase Vault (encrypted at rest with AES-256)
	•	TINs in monitored_clients: encrypted at the column level using pgcrypto or Supabase Vault
	•	JWK private key: stored in Supabase Vault, never in source code or environment variables directly
	•	All API calls to IRS: HTTPS only (required by IRS)

7.2 Row Level Security
All Supabase tables must have RLS enabled. Users can only access their own rows. The polling Edge Function uses a service role key with appropriate scoping.
7.3 Audit Trail
The alert_log and transcript_snapshots tables serve as an audit trail. Raw API responses are stored in transcript_snapshots.raw_response for compliance purposes. Consider a retention policy (e.g. 7 years to match IRS record-keeping requirements).
7.4 IRS Compliance Notes
	•	The ISP application must not store or display unmasked taxpayer data beyond what the IRS API returns (transcripts are already masked)
	•	User consent can be revoked at any time via the IRS Consent App — the system must handle revoked consent gracefully
	•	JWK certificates must be tracked for expiration and renewed before expiry
